# 秒杀接口 QPS 梯度扫描实验（找拐点）

本目录用于完成**梯度压测实验**：固定压测时长，并发数从低到高递增扫描，
持续压测秒杀抢购接口，通过「吞吐随并发的增长曲线」定位 QPS 的大致拐点
（吞吐不再随并发线性增长、延迟/失败率开始抬升的并发档位）。

参考 `../seckill-purchase/` 的配置与数据生成方式，本目录只做梯度扫描，
不复用其双方案交替对比流程。

## 被测接口

| 方案 | 接口 | 说明 |
|------|------|------|
| 异步 | `POST /seckill/purchase` | Redis Lua 一人一单 + 库存预扣 + 落本地秒杀单 + MQ 异步建单 |
| 普通 | `POST /seckill/plain/purchase` | Redis SETNX 一人一单 + DB 条件扣库存 + 请求内同步建真实订单 |

两个方案各扫一遍，可对比两者的拐点位置差异（预期异步拐点更靠后）。

## 文件说明

| 文件 | 说明 |
|------|------|
| `qps-async-cont.jmx` | 异步方案持续压测模板（loop=-1 + `${__P(DURATION,20)}` 固定时长） |
| `qps-plain-cont.jmx` | 普通方案持续压测模板（同上） |
| `qps-users-async.csv` | 异步方案用户池（`press_` 前缀），由 `BatchRegisterAppTest` 生成 |
| `qps-users-plain.csv` | 普通方案用户池（`press_` 前缀），由 `BatchRegisterAppTest` 生成 |
| `run.sh` | 梯度扫描脚本：重建活动 → 生成双用户池 → 逐档位压测 → 汇总拐点 |

## 实验设计

- **变量**：并发数（线程数）从 `START` 到 `END` 按 `STEP` 递增
- **固定量**：单档位压测时长 `DURATION`（默认 20s，含 ramp-up 2s）、
  用户池大小 `USER_COUNT`（默认 200）、库存 100000/SKU
- **每档位流程**：重置数据（清订单 + 清一人一单标记 + 重置库存）→
  持续压测 `DURATION` 秒 → 保存 jtl
- **指标**：总 QPS（请求数/实际时间跨度）、成功数、失败率、平均耗时
- **拐点判据**：吞吐增长率首次显著放缓（< 前档增长率的 30% 且 < 10%）
  且后续不再回升的档位；同时结合失败率抬升位置人工确认

> 说明：持续压测下用户池会被一人一单耗尽，后续请求快速拒绝。
> 因此「总 QPS」统计的是**服务端处理能力（含快速拒绝）**，与
> `seckill-purchase/README.md` 的统计口径一致。

## 使用方法

### 一键梯度扫描（自动重新生成数据）
```bash
./run.sh 10 100 10 20 200 1
# 参数: [起点并发] [终点并发] [步长] [单点时长s] [用户数] [重生成数据 1/0]
```
脚本自动完成：
1. `mvn test` 执行 `SeckillPressDataInitTest` —— 重建秒杀活动 900001
   （RUNNING，2 小时窗口）+ 预热 Redis 库存
2. `mvn test` 执行 `BatchRegisterAppTest` 生成用户池（固定前缀 `press_`，
   `${USER_COUNT}` 个用户），一次生成后复制为 `qps-users-async.csv` 与
   `qps-users-plain.csv`（两方案用户池内容一致，省一次 Spring Boot 启动）
3. 逐档位扫描：并发 10 → 100（步长 10），每档位先重置数据，
   再对异步/普通方案各持续压测 20s
4. 汇总：输出每档位的总 QPS / 成功数 / 失败率 / 平均耗时，
   并给出拐点识别结果

### 扫得更细（找精确拐点）
```bash
./run.sh 60 140 5 30 500 0   # 在疑似拐点附近缩小步长、延长时长
```

### 手动单点压测（沿用现有数据）
```bash
jmeter -n -t qps-async-cont.jmx -JTHREADS=100 -JDURATION=30 -JRAMP=3 -l async-t100.jtl
jmeter -n -t qps-plain-cont.jmx -JTHREADS=100 -JDURATION=30 -JRAMP=3 -l plain-t100.jtl
```

### 前置条件（与 seckill-purchase 相同）
- 走网关 `http://localhost:9000`（网关负责把 JWT 解析为 `X-Auth-User` 头）
- Sentinel 限流：压测前把 `seckill:purchase` 与网关 `/seckill/**`
  的 QPS 限流调高到 5000（Nacos `seckill-service-flow-rules` /
  `gateway-flow-rules`），否则扫到的是限流器拐点而非服务能力拐点
- 用户池 CSV 具有时效性（token 过期、用户积累订单），建议每次带参数 `1`
  重新生成

## 拐点解读

- **拐点之前**：吞吐随并发近似线性增长，说明服务端资源未饱和，
  延迟平稳
- **拐点之后**：吞吐增速放缓直至平台期，延迟开始抬升、失败率上升，
  说明已进入资源瓶颈（连接池/线程池/DB/Redis 任一饱和）
- **异步 vs 普通**：异步方案把建单移出请求链路，预期拐点并发更高、
  拐点处 QPS 更大；对比两者拐点可量化异步化的吞吐收益

## 实测参考（本机，单点 10s，用户池 50）

| 并发 | 异步 QPS | 普通 QPS | 异步平均 | 普通平均 |
|------|----------|----------|----------|----------|
| 10   | 1420 | 1139 | 6.2ms | 7.9ms |
| 20   | 1917 | 1402 | 9.6ms | 13.2ms |
| 30   | 2079 | 1421 | 13.3ms | 19.9ms |
| 40   | 2173 | 1280 | 17.2ms | 29.1ms |
| 50   | 1983 | 1270 | 23.5ms | 36.8ms |

- 异步峰值在并发 40（约 2173 QPS），平台期约从并发 30 开始；
  普通峰值在并发 30（约 1421 QPS），此后吞吐回落
- 异步峰值吞吐比普通高约 **53%**，与 `seckill-purchase` 对比实验
  （+49%~53%）结论一致
- 失败率 99%+ 是持续压测下一人一单耗尽的快速拒绝（预期现象），
  总 QPS 统计的是服务端处理能力（含快速拒绝）
- 用户池越大（`USER_COUNT` 参数），快速拒绝占比越低，成功 QPS 信号越清晰；
  建议正式实验用户池 ≥ 并发上限
